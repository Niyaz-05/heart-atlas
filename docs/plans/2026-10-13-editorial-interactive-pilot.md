## 1. Результат первой поставки

Не строить новую энциклопедию или универсальную CMS. Довести до рабочего состояния один сквозной процесс:

`врач готовит материал → редактор собирает страницу → врач-рецензент проверяет конкретную версию и все состояния → maintainer публикует → обновление не наследует старое одобрение автоматически`.

Пилот: три материала — «Клапаны сердца», «Эхокардиография», «Митральная регургитация». Перед правкой двух последних найти фактические slug в текущем checkout, не создавать дубликаты.

Результат для читателя: пошаговое объяснение клапанов, учебный кликабельный образец ЭхоКГ, связанный материал о заболевании. Результат для врача: шаблон, ссылка на итоговый предпросмотр, понятное авторство и рецензирование. Результат для разработчика: новые статьи используют данные и разрешённые компоненты, а не собственные программы.

### Не входит в первую поставку

- Загрузка пользовательских ЭКГ, PDF, DICOM и медицинских заключений.
- Диагностический чат-бот, интерпретация личных показателей, подбор лечения.
- Новая физиологическая модель или непрерывные «медицинские» ползунки.
- Полное обновление дизайна, перенос всех статей в новый формат, новая база данных.
- Собственные аккаунты, биллинг, совместное редактирование в реальном времени.
- Открытая регистрация в CMS и массовое подключение внешних авторов.
- Замена Astro, переписывание SVG на React, перенос публичного сайта с GitHub Pages.

## 2. Что уже есть и должно остаться

В текущих исходниках есть Astro Content Collections, MDX и React islands; `Diagram`, `HeartModel`, `EcgMonitor`, `HeartSounds`, `Quiz`, `Structure`, `Patient`, `Student`; отдельные YAML-файлы тестов; поиск, треки, embeds и PWA. В CI уже есть lint, typecheck, unit, i18n, build, e2e, Lighthouse, проверка внутренних ссылок и бюджета JavaScript. [R1–R5]

Не дублировать эти подсистемы. В частности, вопросы уже загружаются из соседнего `<slug>.quiz.yaml` через `<Quiz />`. Новые интерактивные данные можно организовать по той же схеме. [R3, R4]

Существующий `review` хранит имя и дату. В прочитанной схеме нет отдельного статуса публикации, а `articlePages` группирует переданные статьи без проверки редакционного статуса. Это точки расширения, не основание объявлять весь проект небезопасным. [R2, R6]

## 3. Архитектурные решения

### ADR-1. Источник истины — Git

Текст остаётся в `content/<locale>/<type>/<slug>.mdx`. Редактор изменяет эти же файлы и связанные YAML. Не хранить параллельно редактируемые версии одной статьи в БД и Git.

Изменения идут через ветку и pull request. Публичный сайт собирается из `main`. Непубликованные статьи не должны попадать в публичную сборку, но файлы и ветки публичного репозитория всё равно публичны: это не место для конфиденциальных черновиков или данных пациентов.

### ADR-2. Разделить три состояния

1. `publication`: `draft | published | withdrawn` — должно ли содержание попадать на публичный сайт.
2. Состояние редакционной работы: draft PR, ready for review, changes requested — остаётся в GitHub, не создаём вторую машину состояний в YAML.
3. Медицинский статус: `unreviewed | verified | needs_review` — вычисляется по записи рецензии, актуальной версии материала и дате повторной проверки.

Опубликованная старая статья может быть честно помечена `unreviewed`. Значок `verified` не является полем, которое автор самостоятельно выбирает в редакторе.

### ADR-3. Новый интерактив — декларативные данные поверх существующих компонентов

Предлагаемая структура одной пилотной статьи:

```text
content/ru/anatomy/
  heart-valves.mdx
  heart-valves.quiz.yaml             # существующий подход
  heart-valves.interactive.yaml      # новый sidecar только при необходимости
```

В MDX:

```mdx
<Interactive id="valves-explainer" />
```

В YAML находятся тип блока, разрешённый сценарий, шаги, подписи, ссылки на источники и текстовая альтернатива. Программный рендерер находится в `apps/web`, а не в `content`.

Старые `<Diagram>`, `<HeartModel>`, `<Quiz>` и другие компоненты продолжают работать. Мигрировать медицинский текст только пилотных страниц. Общая механическая миграция метаданных возможна отдельно и не должна переписывать текст.

### ADR-4. Редактор не является механизмом авторизации публикации

Основной кандидат после пилота — Keystatic для небольшой доверенной редакции. Он поддерживает MDX и пользовательские блоки, но документирует отсутствие поддержки HTML-тегов в MDX. В текущей статье подписи — `<p slot="...">`, поэтому обещать бесшовное редактирование существующего формата нельзя. [R7–R9]

Новый `<Interactive id="..." />` и sidecar позволяют обойти эту конкретную несовместимость без массового переписывания старого контента. Текст, параметры и ссылки должны редактироваться ровно в одном месте.

CMS размещать в отдельном `apps/studio` на Node.js runtime; сайт остаётся статическим. Стандартный GitHub-режим Keystatic требует `write` к репозиторию. Это доступ к репозиторию, а не «только к текстовым полям». `branchPrefix` упрощает интерфейс, но не заменяет модель прав GitHub. На пилоте допускается только доверенный круг с осознанно выданным доступом. Не подключать так всех желающих. [R8]

Первый врач может работать через шаблон и предпросмотр, без CMS и без GitHub. Публичный приём материалов без выдачи `write` — отдельная следующая задача; например, исследовать Decap Open Authoring, но не внедрять две CMS одновременно. [R10]

## 5. HA-01 — зафиксировать базовое состояние

**Действия.** Создать ветку пилота. В обычном checkout установить зависимости по lockfile и выполнить текущие команды, не подменяя версии инструментов случайными глобальными установками:

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
pnpm i18n:check
pnpm build
pnpm e2e
```

Если браузеры Playwright не установлены, использовать команду из текущей документации репозитория. Уже существующие ошибки зафиксировать отдельно; не списывать их на новые изменения.

Добавить `scripts/content-inventory.mjs`, который читает контент как данные и выдаёт JSON и Markdown: id, язык, тип, компоненты, число источников, наличие quiz, текущий review, связанные пресеты и модели. Отчёт должен вычисляться из файлов, а не дублировать вручную счётчик README.

На трёх выбранных страницах сохранить эталон доступных заголовков, ссылок, подписей, вариантов ответов и состояний диаграмм. Screenshots использовать как дополнение к проверке смысла, а не вместо неё.

**Готово, когда:** известна исходная проверяемая база; перечислены используемые конструкции MDX; выбраны реальные пути пилотных статей; текущие URL и RU/EN соответствия зафиксированы.

## 6. HA-02 — добавить управляемую публикацию

**Менять:** `apps/web/src/lib/content.ts`, `apps/web/src/lib/articles.ts`, `apps/web/src/content.config.ts`, потребителей коллекции статей в маршрутах, треках, embeds и post-build. Новые тесты — в существующих `apps/web/test` и `apps/web/e2e`.

Предлагаемые дополнительные поля, не готовый фрагмент текущей схемы:

```yaml
schemaVersion: 2
publication: draft
contributors: []
learningObjectives: []
translationOf: null
```

Не выдумывать имена врачей или авторство при миграции. У действующих материалов явно поставить `publication: published`, сохранив текущий медицинский статус. У новых материалов шаблон ставит `draft`; не использовать бессрочный глобальный default `published`.

Создать один helper, например `getArticleEntries({ visibility: 'public' | 'preview' })`, и через него получать материалы для всех потребителей. Проверить `getCollection('articles')` по всему репозиторию. Фильтрация должна происходить до построения языковых fallback: черновой перевод не должен затенить опубликованный оригинал.

Проверить: прямые article routes, страницы категорий, главную и счётчики, анатомию, треки, embeds, Pagefind, любые feeds/sitemap при их наличии, данные JSON и service worker. Не утверждать наличие feed/sitemap без инвентаризации.

Для `withdrawn` сохранять URL с короткой страницей об изъятии без ошибочного медицинского текста; удалить содержимое из индекса и текущего офлайн-кэша при обновлении. Нельзя гарантировать удаление сохранённой копии у устройства, которое больше не выходило в сеть.

**Тесты:** RU опубликован, EN черновой — английский fallback не раскрывает черновик. Уникальная строка тестового черновика отсутствует во всём публичном артефакте и поисковом индексе. Обычная сборка не включается в preview-режим через query parameter.

**Готово, когда:** новая статья не появляется публично до явной публикации; существующие URL продолжают работать. Публичность Git-веток отдельно объяснена авторам.

## 7. HA-03 — контракт интерактивных данных

**Добавить:**

```text
apps/web/src/lib/interactive.ts
apps/web/src/lib/interactive-registry.ts
apps/web/src/components/interactive/Interactive.astro
apps/web/test/interactive.test.ts
```

Дополнить `content.config.ts` коллекцией для `**/*.interactive.yaml`; id строить аналогично quiz. Зарегистрировать `Interactive` в `article-components.ts`.

Минимальный реестр: `diagram`, `guided-diagram`, `report-explorer`. На первом PR реализовать только адаптер `diagram`; следующие типы добавляются отдельно.

У реестра должны быть: идентификатор типа, схема props, перечень допустимых ресурсов, рендерер, политика статического fallback и список зависимостей, медицинские изменения которых влияют на рецензию. Схема не должна разрешать произвольный путь к компоненту, HTML, скрипт или функцию из контента.

Пример предлагаемого sidecar — иллюстрация контракта, не готовый медицинский материал:

```yaml
schemaVersion: 1
blocks:
  - id: valves-explainer
    kind: guided-diagram
    diagram: heart-valves
    title: Как работают клапаны
    fallback: Текстовое объяснение, согласованное с врачом.
    steps:
      - id: step-1
        state: diastole
        title: Первый этап
        text: Пояснение автора, проверенное рецензентом.
        sourceRefs: [openstax-heart]
      - id: step-2
        state: systole
        title: Второй этап
        text: Пояснение автора, проверенное рецензентом.
        sourceRefs: [openstax-heart]
```

`diastole`/`systole` — существующие состояния `heart-valves`. Не добавлять в YAML вымышленные состояния, для которых нет реализации.

Подписи sidecar рендерить как разрешённый текст с отдельными ссылками на источники, а не передавать произвольный HTML в `set:html`. У `Diagram.astro` выделить общий путь рендеринга для legacy slots и новых типизированных captions. Текст подписи не дублировать в MDX и YAML.

**Источники.** Добавить стабильный `id` каждому источнику пилотной статьи и новый `<Cite refs={['openstax-heart']} />`. Сохранить `<Cite n={1} />` для старого контента. Отображаемую нумерацию вычислять автоматически. Пока статья использует числовые ссылки, редактор не должен разрешать свободное удаление/перестановку источников без атомарного перенумерования всего MDX, quiz и sidecar. Расширить ссылочную валидацию для всех форматов.

**Готово, когда:** блок выбирается по id; неизвестный state, sourceRef или type останавливает проверку; старая статья рендерится прежним способом; удаление используемого источника невозможно незаметно.

## 8. HA-04 — безопасный авторский формат

MDX поддерживает JavaScript, imports и exports; это не формат недоверенного текста по умолчанию. [R11]

Добавить `scripts/check-content-safety.mjs` и тестовые fixtures. Проверять исходный AST до компиляции/исполнения: разрешённые компоненты, props, литеральные строки/числа/булевы значения/массивы/объекты; запрещены ESM, функции, вызовы, spreads, обработчики событий, произвольные выражения и исполняемые URL. Исторические допустимые HTML-подписи обрабатывать узким явным legacy-правилом, не общей поблажкой для любого HTML.

Регистрация разрешённых имён в `article-components.ts` сама по себе не ограничивает все возможности MDX. Проверка безопасности должна запускаться до Astro build во всех путях предпросмотра и в CI. Validator не должен импортировать проверяемую статью или применять `eval` к её props.

Добавить негативные fixtures: import, вызов функции в prop, spread, неизвестный компонент, неизвестная структура, небезопасная ссылка. После ошибки не должен запускаться renderer этой статьи.

Не выдавать AST-фильтр за полноценную песочницу для произвольного кода. Недоверенный PR также может менять конфигурацию, npm scripts и workflow. Поэтому сборки внешних PR изолированы от секретов, выполняются с минимальными правами; привилегированный pipeline не делает checkout и исполнение такого кода. [R12]

**Готово, когда:** недопустимые конструкции детерминированно отвергаются; проверки невозможно обойти простым скрытием поля в CMS; public preview не получает production/editor secrets.

## 9. HA-05 — предпросмотр как часть редакционного процесса

**Добавить:** отдельный preview workflow и режим сборки, например `HA_CONTENT_MODE=preview`. В режиме production — только публичные материалы; в preview видны выбранные черновики с заметным предупреждением.

Выбрать одно окружение для статических preview, отдельное от GitHub Pages production и от origin админки. Публиковать готовые статические артефакты, не выполнять сборку PR в окружении с секретами админки. Конкретный провайдер и его тариф здесь не предположены: перед развёртыванием проверить подходящий текущий тариф, защиту preview и лимиты.

Привилегированный deploy-этап не исполняет содержимое артефакта как скрипт, проверяет происхождение workflow, репозиторий и SHA, не доверяет произвольным путям из архивов. Внешние PR — только после maintainer approval. Не использовать `pull_request_target` для сборки непроверенного кода. [R12]

У preview обязательны noindex, отметка «Черновик», короткий SHA, явное отсутствие service worker и корректный `BASE_PATH`. Noindex не является авторизацией. Удалять preview после закрытия PR; для чувствительных черновиков нужны отдельные непубличные хранилища, в пилоте они не используются.

В PR выводить ссылку на конкретную статью, SHA и checklist. Сначала достаточно CI summary и ручной передачи ссылки врачу; не создавать бота ради одного комментария.

Проверяется та же страница и те же компоненты, что попадут в production, а не упрощённая CMS-карточка. Дать рецензенту переключатель уровня и список всех состояний/шагов/ответов.

**Готово, когда:** врач открывает готовую страницу без Node/GitHub checkout; видит точную версию; из preview нельзя случайно опубликовать статью; черновик не попадает в production PWA.

## 10. HA-06 — проверка версии и подтверждения рецензента

**Добавить:**

```text
editorial/reviews/
editorial/reviewers.yaml
apps/web/src/lib/review-state.ts
scripts/check-medical-review.mjs
scripts/build-content-fingerprints.mjs
```

Названия предложены. Публичные профили специалистов хранить отдельно от внутренних сведений о верификации. Документы, удостоверяющие квалификацию, не размещать в Git. Имена/специальности — только с согласия специалиста.

Запись рецензии включает `articleId`, язык, `reviewerId`, дату, digest проверенного пакета, область проверки и дату следующей проверки. Последняя — редакционный срок, а не медицинская гарантия. Проект сам выбирает сроки; не выдавать один интервал за универсальный стандарт.

Digest считать детерминированно из текста, медицинских метаданных и источников, quiz, interactive sidecar, нужных схем/визуализаций/моделей/пресетов и локализованных медицинских подписей. Запись самой рецензии из digest исключается — иначе её добавление создает циклическое изменение версии. Полный SHA репозитория хранить для аудита, но не использовать единственным ключом: правка несвязанного README не должна сбрасывать все рецензии.

На пилоте допустим консервативный список зависимостей: лишняя повторная проверка лучше незаметного изменения смысла. Не считать ручное увеличение `componentVersion` гарантией: изменения файлов должны выявляться автоматически. Список зависимостей сам входит в проверяемый набор и защищён от незаметного удаления.

Подтверждение — не только YAML. На первом этапе maintainer фиксирует проверяемое согласование врача на конкретный preview/digest; при GitHub-рецензировании проверяется утверждённая личность и актуальный PR. Автор не подтверждает свою же статью. Добавить независимый технический review для правок кода/схем/валидаторов. Не создавать фальшивого второго участника для одиночной команды.

Настроить требуемые проверки `main`, обязательные PR и отклонение устаревших approvals. CODEOWNERS полезен для редакционных записей и исполняемых файлов, но список нескольких code owners не гарантирует два разных типа одобрения: при необходимости это проверяет отдельный gate. [R13]

**Правила публикации.** Старые непроверенные статьи остаются такими. Новые пилотные материалы выходят после рецензии. Обычная новая версия уже проверенной статьи ждёт проверки в ветке, а production продолжает показывать прежнюю версию. Изменение общей медицинской визуализации показывает все затронутые проверенные статьи до merge.

Экстренное исправление/изъятие допускается по отдельному maintainer-процессу с причиной и снятием неподходящего значка; не задерживать удаление опасной ошибки ради обычного цикла. Просрочка плановой проверки создает очередь и честное обозначение актуальности, а не «вечную» зелёную отметку.

**Тесты:** правка quiz, подписи шага или связанного сценария снимает совпадение digest; правка несвязанного файла — нет; автор не может сам поставить verified; перевод не наследует рецензию оригинала; digest не меняется от добавления записи о нём.

## 11. HA-07 — GuidedDiagram

**Добавить:** `apps/web/src/components/interactive/GuidedDiagram.astro`, небольшой клиентский контроллер при необходимости и соответствующие unit/e2e tests.

Первый renderer связывает текстовые шаги с существующей схемой: «Назад / Дальше», номер шага, подпись, источники, явная кнопка запуска движения. Клавиатура, mobile layout, статический список всех шагов без JS. Не начинать с scroll-driven синхронизации 3D, ЭКГ и Wiggers: это отдельный более сложный этап.

Состояние принадлежит экземпляру блока, а не глобальной переменной страницы. Два блока на странице не переключают друг друга. Не подменять доступное radio-управление простым визуальным CSS-хаком без обновления состояния элементов управления.

Узкий адаптер к `Diagram` получает `state` из проверенного списка. Существующий диаграммный движок остаётся общим; не рисовать копию клапанов внутри GuidedDiagram.

Для первого пилота достаточно последовательности по двум имеющимся состояниям `heart-valves`. Для четырёх фаз потребуется отдельно добавить недостающие состояния в код и проверить их с врачом; редактор не должен имитировать наличие такого сценария.

**Готово, когда:** медицинское пояснение и визуальное состояние всегда соответствуют; без JS смысл доступен; режим без движения сохраняется; чужая статья не ломается; бюджет JS не увеличен без обоснования.

## 12. HA-08 — ReportExplorer

**Добавить:** `apps/web/src/components/interactive/ReportExplorer.astro`, схему данных и demo fixture. Данные реального медицинского материала добавляются только на HA-09.

Учебное заключение строить семантическим HTML, не PDF и не одной картинкой с координатами. На desktop — условный протокол рядом с пояснением; на mobile — term buttons и раскрывающиеся пояснения. Список терминов доступен клавиатуре.

У записи термина: стабильный id, подпись, пример формулировки, простое объяснение, при необходимости уточнение для студента, ограничения интерпретации, sourceRefs и ссылка на связанный материал. `referenceRange` и автоматическую классификацию «норма/опасность» в MVP не вводить.

На странице явно указать: «Вымышленный учебный пример, не интерпретация вашего обследования». Не копировать реальные имена, даты, учреждения, QR-коды и номера из медицинских документов. Не добавлять загрузку файлов или поле для личных значений.

**Готово, когда:** читатель выбирает термин и получает согласованное объяснение и ограничения; страница читается и печатается без JS; никакие пользовательские медицинские данные не вводятся и не отправляются.

## 13. HA-09 — медицинский пилот

Подготовить шаблон автора в `docs/medical-author-template.md` и инструкцию рецензента в `docs/medical-review.md`. Не требовать от врача MDX, YAML, git или создания анимации.

Шаблон: аудитория; 2–3 учебных результата; основное объяснение; частое заблуждение; подписи каждого состояния/шага; источники; ограничения модели; вопросы для проверки понимания. Для интерактива врач выбирает цель: показать структуру, сравнить состояния, пройти последовательность, разобрать термин.

Пилотные поставки:

- «Клапаны сердца»: один GuidedDiagram, существующая модель и quiz без лишнего дублирования.
- «Эхокардиография»: один ReportExplorer с согласованным учебным примером.
- «Митральная регургитация»: существующие визуальные возможности, понятные переходы к клапанам и ЭхоКГ; не добавлять новый симулятор.

Работать сначала с RU-версией пилота. EN-версию не объявлять проверенной по факту существования RU-рецензии. При сохранении старого перевода явно отслеживать его соответствие; при выводе fallback учитывать правила HA-02.

Попросить автора и отдельного рецензента пройти процесс. Провести небольшие сессии с читателями: попросить своими словами объяснить цель материала и ограничения. Это качественная проверка, не доказательство клинической эффективности.

**Готово, когда:** проверены не только абзацы, но и шаги, подсказки, источники, варианты ответов, static fallback и итоговый preview; записаны реальные затруднения врача при подготовке материала.

## 14. HA-10 — Keystatic: проверка совместимости

Создать экспериментальное `apps/studio` и конфигурацию `keystatic.config.ts`. На этом этапе можно работать локально, без развёртывания и новых production-секретов. Проверить monorepo root и пути записи: редактор должен менять именно корневой `content/`, а не создавать копию в `apps/studio/content`.

Редактировать только пилотный поддерживаемый формат. Минимум: metadata, текст, Patient/Student, Cite со стабильными ссылками, Interactive по id, поля соответствующего sidecar, quiz. Остальной контент не открывать на запись до проверки совместимости.

Не обещать, что Keystatic из коробки даст единый экран для трёх связанных файлов. В пилоте допустимы связанные коллекции и ясные ссылки между ними. Единая форма и атомарное сохранение нескольких файлов — отдельная задача после проверки API. Несогласованное промежуточное состояние ветки не должно попасть в publication.

Проверка цикла: открыть → сохранить без изменений → изменить один абзац → сохранить → открыть повторно → собрать реальную страницу. Сравнивать семантические данные и визуальный результат, а не только байты: formatter может менять пробелы.

Обязательные случаи: кириллица, RU/EN, вложенные блоки, inline Cite, literal arrays, отсутствующий optional sidecar, quiz правильные ответы, удаление используемого источника, неподдерживаемый legacy HTML. Последний должен явно блокировать сохранение, не исчезать молча.

**Решение:** подключать Keystatic только при успешном прохождении этих тестов. При провале не переписывать весь архив под CMS: зафиксировать blocker, оставить авторов на проверенном шаблоне и доработать узкий поддерживаемый формат.

## 15. HA-11 — редактор для доверенной редакции

Развернуть только `apps/studio` с Node.js API и HTTPS. Добавить GitHub App с минимально необходимыми правами для выбранного репозитория. Секреты находятся только в окружении studio; не в MDX, не в Pages bundle, не в PR previews. [R8]

Рабочий процесс врача: вход → выбрать материал/шаблон → редактировать текст → добавить готовый блок → заполнить подписи/источники → сохранить в `content/…`-ветку → передать на проверку. На первой версии PR может открывать maintainer: не делать собственный backend ради одной кнопки.

Авторы не редактируют записи рецензирования, реестр проверенных специалистов, CODEOWNERS и валидаторы через CMS. Это ограничение интерфейса дополняет PR-политику, но не отменяет фактические GitHub `write`-права. Не называть его изоляцией прав на уровне файлов.

Оставить изображения/файлы выключенными, пока не реализованы список допустимых типов, пределы размеров, безопасная обработка и сведения об авторе/лицензии. Публичный Git не должен стать архивом неразрешённых клинических медиа.

Проверить stale edit/concurrency: редактор не перезаписывает незаметно изменение другого автора; ошибка merge показывается явно. Проверить выход из учётной записи, истечение сессии и недоступность preview/studio из обычной публичной навигации.

**Готово, когда:** один врач через интерфейс меняет материал и добавляет существующий блок, не редактируя исходный код; второй проверяет готовый результат; публикация возможна только после необходимых подтверждений.

## 16. HA-12 — выпуск и обслуживание

Связать пилот в существующий learning track: «Клапаны → ЭхоКГ → заболевание». На главной добавить небольшой вход «Понять заключение»; не начинать глобальный редизайн навигации.

Добавить страницу «Для врачей»: пример материала, роли автора/рецензента, понятный способ связи и шаблон вклада. На MVP допустимы существующий GitHub issue и выбранный публичный контакт maintainer, не требуется собственный сервис обращений.

Рядом со статьёй — источник, автор/рецензент при наличии, дата проверки и понятное состояние. Проверить точность баннера об источниках: `textbook/reference` не называть автоматически клиническими рекомендациями.

Добавить печатный режим для краткого вывода, выбранных проверенных вопросов врачу и списка источников. Предпочесть `window.print()` и print CSS серверной генерации PDF. Вопросы выбирать локально; не записывать диагнозы и чувствительный свободный текст в share URL.

Если нужна аналитика, сначала определить события без персональных медицинских данных: открытие блока, прохождение шага, завершение, переход к связанному материалу. Не отправлять медицинские документы, свободный текст, индивидуальные ответы quiz или поисковые запросы «на всякий случай». До выбора правомерного способа сбора достаточно наблюдаемых пользовательских сессий и агрегатов редакционного процесса.

Предлагаемые пилотные критерии, не отраслевые нормы: три материала прошли весь цикл; автор смог внести правку и собрать блок без кода; повторное открытие CMS не исказило контент; независимый review привязан к версии; тесты и текущие бюджеты зелёные; у каждого материала есть ответственный за обновление.

Периодическая GitHub Actions задача может формировать единый issue об устаревших проверках, битых источниках и затронутых материалах. Сначала расширить существующую проверку ссылок, а не плодить отдельный issue на каждую статью. Такая автоматизация не заменяет медицинское перечитывание новых рекомендаций.

## 17. Общая приёмка

### Публикация

- Черновик не появляется ни по прямому публичному URL, ни в embed, ни в поиске, треке, счётчиках и новом PWA-кэше.
- Fallback языка выбирается среди разрешённых материалов.
- Preview помечен, привязан к версии, без service worker и на отдельном origin.
- Изъятая статья не продолжает раздаваться новой сборкой; ограничения удаления старых офлайн-копий документированы.

### Формат и источники

- Старые статьи работают без массовой переписи.
- Новый блок имеет одного владельца данных; подписи не продублированы.
- Перестановка источников не меняет незаметно смысл ссылок.
- Недопустимый MDX отклоняется до выполнения.
- Проверка DOI/URL не выдаётся за подтверждение медицинского тезиса.

### Рецензирование

- Автор не ставит себе verified.
- Изменение текста, quiz, схемы или подписи требует подходящей проверки.
- Фиксация рецензии не меняет digest того, что она подтверждает.
- Перевод не наследует медицинское одобрение автоматически.
- Есть процесс срочного снятия ошибочного материала.

### Интерфейс

- Проверены keyboard, mobile, reduced motion, no-JS, печать.
- Несколько интерактивов не конфликтуют друг с другом.
- 3D и тяжёлый JavaScript не подгружаются до необходимости.
- Пилот не ухудшает текущие performance/accessibility проверки.

## 18. Что сделать первым

Начать не с редактора, а с HA-01 и HA-02. Параллельно согласовать с врачом содержание трёх пилотных материалов. Следующим PR реализовать HA-03 только для одного существующего Diagram. После него — HA-04 и HA-05, затем HA-06.

Таким образом, ещё до новой визуализации и CMS появится небольшой, полезный результат: материал можно подготовить, безопасно показать врачу и опубликовать с понятным статусом. GuidedDiagram и ReportExplorer добавляются поверх этого процесса, а не вместо него.
